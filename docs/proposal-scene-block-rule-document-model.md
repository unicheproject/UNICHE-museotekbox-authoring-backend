# Decision proposal — Scene / Block / Rule feature layer (document model)

Status: **approved** — this is the chosen write model for Scene/Block/Rule (see
`docs/scene-block-rule-write-model-comparison.md`). Not yet implemented. Written
against `docs/decision-template.md`'s format.

This is the alternative to
[`proposal-scene-block-rule.md`](./proposal-scene-block-rule.md) — same entities,
same business requirement, same card-type-binding fix, same out-of-scope items
(score/state variables, conditions, effects). What differs is entirely *how the API
is written and read*: one versioned document per experience, instead of separate
CRUD endpoints per Scene/Block/Rule. Written up as its own document so the two can be
compared side by side before picking one, per an explicit request not to just default
to whichever was already written down.

## Business requirement

Same as the other proposal: Scene is a chapter, Block is content inside a scene,
Rule says what happens when something occurs (most importantly, a physical object
being scanned).

## The core idea: one document, one endpoint

```
GET  /api/v1/projects/{projectId}/experience
PUT  /api/v1/projects/{projectId}/experience
```

- `GET` returns everything at once: every scene in the project, each with its blocks
  and rules nested inside, plus a version number.
- `PUT` sends the *entire* document back — every edit, every newly added scene/block/
  rule, with anything removed simply left out — guarded by an `If-Match` header
  carrying the version number the client last read.
- There is no `POST`/`PATCH`/`DELETE` for an individual scene, block, or rule at all.
  Every kind of change — rename a scene, add a block, delete a rule, reorder
  anything — happens the same way: edit the document locally, `PUT` the whole thing
  back.

## How identity works without per-row endpoints

The per-entity proposal gets a scene's identity for free from the URL
(`PATCH /scenes/101` obviously means scene 101). Without per-row endpoints, something
else has to say "this array item is the same scene as before, just edited" versus
"this is a brand new scene" — and let a new rule reference a new scene, both created
in the same `PUT`, before either has been saved to the database yet.

The fix: every scene, block, and rule gets its own permanent string key (`scene_key`,
`block_key`, `rule_key`) — separate from its internal numeric row id, never reused
even after the row is deleted, and never changed by a rename or reorder. A rule's
target isn't `target_scene_id` pointing at a row that may or may not exist yet — it's
`target_scene_key`, a value the client can invent locally for a scene it's creating in
the very same request. The server only checks that a new key is well-formed and not
already used at or below the project's own running counter, then keeps it exactly as
given — it never renames a key.

## Concurrency: version instead of last-write-wins

`GET` returns a version number (also sent as an `ETag`). `PUT` must send that value
back as `If-Match`. If someone else's `PUT` already landed and bumped the version, this
`PUT` is rejected with `409` and the current document is returned, instead of
silently overwriting whatever the other save just did. This is what actually solves
the concurrent-edit-clobbering risk the per-entity proposal's discussion flagged
against a naive "resend the whole scene" approach — a real version check, not just
resending the full document.

## Database changes

Same three tables as the other proposal, plus a stable key column on each and three
new columns on `projects` for key generation and optimistic concurrency:

```sql
--changeset museotekbox:0011-create-scenes
CREATE TABLE scenes (
    id                 BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id         UUID         NOT NULL,
    scene_key          VARCHAR(64)  NOT NULL,
    name               VARCHAR(255) NOT NULL,
    position           INTEGER      NOT NULL,
    is_start           BOOLEAN      NOT NULL DEFAULT FALSE,
    init_card_type_id  BIGINT,
    CONSTRAINT fk_scenes_project FOREIGN KEY (project_id) REFERENCES projects (id),
    CONSTRAINT fk_scenes_init_card_type FOREIGN KEY (init_card_type_id) REFERENCES scan_object_types (id),
    CONSTRAINT uk_scenes_project_key UNIQUE (project_id, scene_key)
);

--changeset museotekbox:0012-create-blocks
CREATE TABLE blocks (
    id       BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    scene_id BIGINT       NOT NULL,
    block_key VARCHAR(64) NOT NULL,
    type     VARCHAR(31)  NOT NULL,
    position INTEGER      NOT NULL,
    content  JSONB        NOT NULL DEFAULT '{}',
    CONSTRAINT fk_blocks_scene FOREIGN KEY (scene_id) REFERENCES scenes (id),
    CONSTRAINT uk_blocks_scene_key UNIQUE (scene_id, block_key)
);

--changeset museotekbox:0013-create-rules
CREATE TABLE rules (
    id                   BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    scene_id             BIGINT       NOT NULL,
    rule_key             VARCHAR(64)  NOT NULL,
    event_type           VARCHAR(31)  NOT NULL,
    action               VARCHAR(31)  NOT NULL,
    position             INTEGER      NOT NULL,
    scan_object_type_id  BIGINT,
    trigger_block_key    VARCHAR(64),
    target_scene_key     VARCHAR(64),
    target_block_key     VARCHAR(64),
    CONSTRAINT fk_rules_scene FOREIGN KEY (scene_id) REFERENCES scenes (id),
    CONSTRAINT fk_rules_scan_object_type FOREIGN KEY (scan_object_type_id) REFERENCES scan_object_types (id),
    CONSTRAINT uk_rules_scene_key UNIQUE (scene_id, rule_key)
);

--changeset museotekbox:0014-add-experience-doc-columns
ALTER TABLE projects
    ADD COLUMN next_scene_seq INTEGER NOT NULL DEFAULT 1,
    ADD COLUMN next_block_seq INTEGER NOT NULL DEFAULT 1,
    ADD COLUMN next_rule_seq  INTEGER NOT NULL DEFAULT 1,
    ADD COLUMN doc_version    INTEGER NOT NULL DEFAULT 0;
```

Note `rules.target_scene_key`/`target_block_key`/`trigger_block_key` are plain
`VARCHAR`, not foreign keys — they're resolved and validated by application code
during the write's own validation pass (see below), not by the database, since
Postgres can't enforce "this string matches some other row's key column" as a real
FK the way a numeric id reference can.

`is_start`, `init_card_type_id`, and `scan_object_type_id` (instead of
`scan_object_id`) are the same fixes as the other proposal, for the same reasons —
see that document for the full explanation.

## Write algorithm

```
PUT /api/v1/projects/{projectId}/experience
If-Match: 7

1. validate keys       every key is well-formed and unique within this document
2. validate graph      every target key resolves to something in this document;
                        exactly one scene has is_start = true
3. validate freshness  no new key is at or below the project's stored counter
4. diff + apply        match existing rows by key (update), keys not seen before
                        are inserts, rows whose key is missing from the document
                        are deletes — all in one transaction
5. bump version         return the fresh document with its new version

stale If-Match -> 409 + the current document
```

## Where this differs from the per-entity proposal

- **No small, targeted edits.** Moving one block means resending the entire
  experience document. For a large experience (many scenes), that's a bigger payload
  on every save than the per-entity proposal's "just this one block" request.
- **The scene→project permission-check lookup problem disappears for free.** The
  other proposal's "implementation note" flagged that Block/Rule endpoints need an
  extra database read to resolve which project a scene belongs to, since they only
  get `sceneId` from the URL. Here, every request is already scoped by `projectId` in
  the URL — there's nothing to resolve.
- **Cross-project references become structurally harder to create**, since the whole
  document is read and written as one project-scoped unit — but this still needs the
  same *validation-pass* check as the other proposal (step 1–2 above), it isn't
  automatically impossible just because the document is project-scoped.
- **Deletion policy — decided: block the whole Save.** Matches the per-entity
  proposal's policy. If a key drops out of the document and something else still
  targets it (a rule's `target_scene_id`/`target_block_id`/`trigger_block_id`), step
  2 (validate graph) rejects the entire `PUT` with a 4xx before anything is applied —
  no partial apply, no nulled-out dangling references. The null-and-flag alternative
  (delete succeeds, dangling refs nulled, experience marked "incomplete") was
  considered and rejected in favor of consistency with the other model and because
  the write algorithm already validates the graph before applying, so blocking here
  is a natural fit rather than new machinery.
- **Testing shape is different.** Fewer, larger tests around one whole-document
  validate/diff/apply cycle (malformed keys, unresolvable target keys, more than one
  `is_start`, stale `If-Match`, concurrent `PUT`s), instead of many small per-operation
  tests per entity.

## Open questions specific to this model

1. **Payload size and performance** once an experience has many scenes — there's no
   way to fetch or save part of the document; it's always all-or-nothing.
2. **Autosave.** A whole-document `PUT` on every small change (e.g. every few seconds
   while an author is mid-edit) is expensive and races against a manual save far more
   than a per-entity `PATCH` would. Needs a decision on how/whether the authoring UI
   debounces or batches edits before saving.
3. ~~**Deletion policy**~~ — decided above: block the whole Save.

## Decision

This document originally deliberately didn't pick a winner between the two models.
That decision has now been made: **document model chosen** — see
`docs/scene-block-rule-write-model-comparison.md` for the reasoning (driven mainly by
the frontend's batched-Save plan, which removes this model's biggest cost while
exposing real gaps — no atomicity, no ordering story, no conflict detection — in the
per-entity alternative).
