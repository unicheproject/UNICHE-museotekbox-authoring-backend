# Decision proposal — Scene / Block / Rule feature layer (per-entity REST model)

Status: **not chosen** — the document model
(`proposal-scene-block-rule-document-model.md`) was picked instead; see
`docs/scene-block-rule-write-model-comparison.md` for the reasoning. Kept for
reference, not deleted. Written against `docs/decision-template.md`'s format.

This is one of two competing write-model proposals for the same feature, kept as
separate documents so both can be compared side by side before picking one — see
[`proposal-scene-block-rule-document-model.md`](./proposal-scene-block-rule-document-model.md)
for the alternative (one versioned document per experience, instead of separate CRUD
endpoints per Scene/Block/Rule as designed here). Everything else in this document —
the entity fields, the deletion/reference rules, the card-type-binding fix, the
out-of-scope items — applies to both; only the API shape and write mechanics differ.

## Scope

Scene, Block, and Rule are three new database tables that all belong to a Project
(what the product UI calls an "Experience"). They depend on each other — a Rule
points at a Scene, a Block, and a ScanObject — so this proposal designs all three
together. It recommends building and shipping them one at a time rather than all at
once (see the commit plan at the end).

## Business requirement

This is what lets an author actually build the content of an Experience:

- A **Scene** is one "chapter" of the experience.
- A **Block** is a piece of content inside a scene — text, an image, a video, a
  quiz, a button, or a true/false question.
- A **Rule** says what happens when something occurs — most importantly, when a
  visitor scans a physical object — for example "when this card is scanned, go to
  this scene" or "when this quiz is answered correctly, show this block."

Everything built so far (organisations, projects, boxes, scan objects) exists to
support this — this is the actual product feature, not scaffolding around it.

## Database changes

Three new tables: `scenes`, `blocks`, `rules`.

```sql
--changeset museotekbox:0011-create-scenes
CREATE TABLE scenes (
    id                 BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id         UUID         NOT NULL,
    name               VARCHAR(255) NOT NULL,
    position           INTEGER      NOT NULL,
    is_start           BOOLEAN      NOT NULL DEFAULT FALSE,
    init_card_type_id  BIGINT,
    CONSTRAINT fk_scenes_project FOREIGN KEY (project_id) REFERENCES projects (id),
    CONSTRAINT fk_scenes_init_card_type FOREIGN KEY (init_card_type_id) REFERENCES scan_object_types (id)
);

--changeset museotekbox:0012-create-blocks
CREATE TABLE blocks (
    id       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    scene_id BIGINT       NOT NULL,
    type     VARCHAR(31)  NOT NULL,
    content  JSONB        NOT NULL DEFAULT '{}',
    CONSTRAINT fk_blocks_scene FOREIGN KEY (scene_id) REFERENCES scenes (id)
);

--changeset museotekbox:0013-create-rules
CREATE TABLE rules (
    id                    BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    scene_id              BIGINT      NOT NULL,
    event_type            VARCHAR(31) NOT NULL,
    action                VARCHAR(31) NOT NULL,
    scan_object_type_id   BIGINT,
    trigger_block_id      BIGINT,
    target_scene_id       BIGINT,
    target_block_id       BIGINT,
    CONSTRAINT fk_rules_scene FOREIGN KEY (scene_id) REFERENCES scenes (id),
    CONSTRAINT fk_rules_scan_object_type FOREIGN KEY (scan_object_type_id) REFERENCES scan_object_types (id),
    CONSTRAINT fk_rules_trigger_block FOREIGN KEY (trigger_block_id) REFERENCES blocks (id),
    CONSTRAINT fk_rules_target_scene FOREIGN KEY (target_scene_id) REFERENCES scenes (id),
    CONSTRAINT fk_rules_target_block FOREIGN KEY (target_block_id) REFERENCES blocks (id)
);
```

**`trigger_block_id` is new — not in the original ERD.** Added because
`ANSWER_CORRECT`/`ANSWER_WRONG`/`BLOCK_COMPLETED` events need to say *which* block's
answer or completion they're reacting to. Without it, a scene with more than one quiz
or true/false block would have no way to tell those events apart — "answered
correctly" alone doesn't say which question. `scan_object_type_id` (see below) plays
this same role for `TAG_SCANNED`; `trigger_block_id` is the equivalent for the
block-driven events.

**`scan_object_type_id`, not `scan_object_id` — changed from the original ERD, and
`is_start`/`init_card_type_id` on `scenes` are new.** All three came from reviewing a
colleague's independent design exploration of this same feature and catching a real
gap in the original ERD:

- The original design had `Rule` point at one specific `ScanObject` row — one
  specific physical, RFID-tagged card. That breaks the moment the same experience
  runs on more than one box (already possible today — `Box`↔`Project` is
  many-to-many): each box has its own physical set of cards, so a rule bound to one
  box's specific card would simply never fire on any other box. Binding to
  `scan_object_type_id` instead — an org-defined *type* of card (e.g. "Hint card"),
  which every box can have its own physical instance of — fixes this. **Open
  question, not resolved here:** `scan_object_types` today is just an org-level
  grouping label (e.g. grouping several differently-coloured cards under one type)
  — it may be coarser than what a rule actually needs to distinguish (e.g. "the RED
  card" specifically, not "any coloured card"). Needs product input before Phase 3.
- `is_start` marks which scene the experience begins from — nothing in the original
  design recorded this at all, so there was no way to know where a box should start.
- `init_card_type_id` lets a scene be entered directly by scanning its own card,
  independent of any rule pointing to it — needed for scenes nothing else leads to
  (e.g. a standalone "about this collection" scene), which otherwise would be
  permanently unreachable.

Runtime state — score/flag/timer variables, rule conditions, and effects beyond
simple navigation — is a substantially larger feature the same exploration surfaced.
**Deliberately out of scope for this proposal**, kept as a future phase, not designed
here.

These go in a new migration file, not `01-initial-schema.sql` — that file has already
run in production, so its existing changesets can't be edited, only added to.

**One design decision worth calling out:** `Block`'s `content` column stores its data
as JSON in a single column, rather than each block type (text, image, video, etc.)
having its own dedicated table with its own columns. This was left as an open
question in the original design. The reasoning for JSON: each block type's content is
small and different-shaped, and nothing in the app needs to search or filter by what's
inside a block's content — so a dedicated table per type would add structure without
adding any real benefit.

## API changes

New endpoints only — nothing existing changes:

- `POST/GET/PATCH/DELETE /api/v1/projects/{projectId}/scenes[/{id}]`
- `POST/GET/PATCH/DELETE /api/v1/scenes/{sceneId}/blocks[/{id}]`
- `POST/GET/PATCH/DELETE /api/v1/scenes/{sceneId}/rules[/{id}]`
- `GET /api/v1/projects/{projectId}/scenes/full`

Blocks and rules are scene-owned in the data model (their `scene_id` is required, not
optional) but each still gets its own full set of endpoints, not just inline creation
through the scene. This keeps editing one block or rule a small, targeted request
instead of resending everything else in the scene.

Two read endpoints return nested content, both read-only conveniences — writes always
go through each resource's own endpoint:

- `GET /scenes/{id}` returns one scene together with its own blocks and rules, so the
  authoring UI can load a single scene's editing view in one call.
- `GET /projects/{projectId}/scenes/full` returns the *entire* experience — every
  scene in the project, each with its blocks and rules nested inside. Without this,
  reconstructing the whole experience would mean fetching the scene list, then calling
  each scene's blocks and rules separately (a request per scene). This is also the
  shape the physical box will eventually need: it has to load a whole published
  experience's content to run, not one scene at a time. The plain `GET
  /projects/{projectId}/scenes` list stays lightweight (scene rows only, no nested
  content) for the authoring UI's scene navigator, where the full content isn't
  needed.

There's no endpoint to list all scenes across every project at once — same as how
projects, boxes, and scan objects work today, you always list within one project (or
one scene).

## Frontend needs

An authoring UI for building scenes/blocks/rules. Out of scope for this proposal —
backend only, same as every other feature added so far.

## Dependencies on other services

None new. Every project in this system already goes through a permission check
before it can be read or written — that check calls out to Catalogue (the platform
service that owns organisations, projects, and who's allowed to access them) to
confirm the current user is allowed to touch that project. Scene/Block/Rule reuse
that exact same check, since they all belong to a project. No new endpoint needs to
be added to Catalogue, and no new login permission needs to be added to Keycloak.

## Technical decisions

1. **Block's content is one JSON column, not one table per block type** (explained
   above) — this closes a question left open since the original design.
2. **Scene, Block, and Rule live entirely in this backend's own database.** Unlike
   Project — which is really owned by Catalogue and only mirrored here — nothing
   about a Scene, Block, or Rule exists anywhere else. That means the code for them
   can be simpler than Project's: no background job is needed to keep a local copy in
   sync with an external source, because there is no external source.
3. **Reordering scenes:** each Scene has a plain whole-number `position` column. When
   an author reorders scenes, the update simply renumbers every sibling scene in the
   project from scratch. A project will only ever have a small number of scenes, so
   this simple approach is fine — no need for a more complex scheme designed for
   large lists.
4. **Rule's optional fields are checked in code, not by the database:** a Rule has
   four fields that are sometimes empty depending on what kind of rule it is (which
   object triggers it, which block's answer triggers it, which scene it jumps to,
   which block it shows). Whether a given field is required depends on the rule's
   type — for example, "when this object is scanned" requires the trigger object,
   "when this question is answered correctly" requires the trigger block, "go to this
   scene" requires the target scene. That kind of conditional requirement is checked
   in the backend code when a rule is created or edited, not enforced by the database
   itself. This matches how validation already works everywhere else in this backend.
5. **Deleting a Scene deletes its own blocks and rules automatically** (they belong
   to it), **but is blocked if any *other* rule targets it** — i.e. some rule
   elsewhere has this scene as its `target_scene_id`. Deleting it in that case returns
   an error naming the rule(s) that still point to it; the author has to update or
   delete those first. The same rule applies to deleting a Block that some rule points
   at, whether as its `target_block_id` (the block it shows) or its `trigger_block_id`
   (the block whose answer it's reacting to). This keeps things consistent: a scene's
   own content is always safe to cascade, but nothing that's still *being pointed at
   from elsewhere* can be removed silently.
6. **Cross-project references must be rejected on create/update:** a Rule's
   `target_scene_id`/`target_block_id` must belong to the same project as the rule's
   own scene. Nothing in the database enforces this — the foreign key only checks
   that the target exists somewhere, not that it's in the same project — so it needs
   an explicit check in the application code. `trigger_block_id` is even more
   restricted: since it names the block whose answer this rule is reacting to, it must
   belong to the *same scene* as the rule itself, not just the same project.
7. **Cross-organisation references must be rejected on create/update:** a Rule's
   `scan_object_type_id` points at a ScanObjectType, which belongs to an
   organisation, not a project. The application code must check that the
   ScanObjectType's organisation matches the organisation that owns the rule's own
   project. The same check applies to `Scene.init_card_type_id`.
8. **Exactly one scene per project can be the start scene:** `is_start` is checked in
   application code, not a database constraint — setting a new scene's `is_start` to
   `true` must first clear it on whichever scene in the project currently has it,
   within the same transaction. Same reasoning as decision 4: this kind of
   cross-row invariant isn't something a plain column constraint can express, so it's
   enforced where every other conditional rule in this feature already is.

## Implementation note (not a design decision)

Scene's endpoints get `projectId` directly from the URL, so the permission check is
immediate. Block's and Rule's endpoints only get `sceneId`, so each operation has to
look up that scene first to find out which project it belongs to, before the
permission check can run. This is just one extra database read per Block/Rule
request — not a risk, just worth knowing going in.

## Tests

For each new operation: the normal success case, the not-found case, the
cross-project-reference case, the cross-organisation-reference case, the
same-scene-required case for `trigger_block_id`, the blocked-delete-when-still-targeted
case, and the case where Catalogue says the user isn't allowed to access the project.
Also a test for the scene-reordering logic described above, and for `is_start`
(exactly one scene per project can be the start scene).

## Suggested build order (one phase at a time, not all at once)

**Phase 1 — Scene:**
1. Database migration for the `scenes` table only
2. The Scene entity/table-mapping class and its repository
3. The Create/Get/List/Update/Delete operations for scenes, each starting with the
   project permission check
4. The REST endpoints and their request/response shapes
5. Tests
6. Documentation updates

**Phase 2 — Block**, then **Phase 3 — Rule** (including the reference-blocking and
cross-project/cross-org checks from decisions 5–7 above) — each shipped as its own
proposal and its own set of commits once the previous phase is done, rather than
building all three at once.

`GET /projects/{projectId}/scenes/full` naturally comes after Phase 3, since it
returns Rules too and has nothing meaningful to return until all three exist.

## Resolved questions

Raised and settled during review of this proposal, kept here for traceability:

- **What happens when a Scene that's targeted by another rule gets deleted?** →
  Blocked until the referencing rule is updated or removed (decision 5).
- **What happens when a Block that's targeted by another rule gets deleted?** →
  Same as Scene: blocked until the referencing rule is updated or removed
  (decision 5).
- **Can a Rule's target point at a scene/block in a different project?** → No —
  must be explicitly rejected on create/update (decision 6).
- **Can a Rule's `scan_object_id` point at a ScanObject in a different
  organisation?** → No — must be explicitly rejected on create/update (decision 7).
- **If a scene has more than one quiz/true-false block, how does a rule say which
  block's answer it's reacting to (`ANSWER_CORRECT`/`ANSWER_WRONG`/
  `BLOCK_COMPLETED`)?** → Added a new `trigger_block_id` field to Rule, the equivalent
  of `scan_object_id` but for block-driven events instead of scans; must belong to the
  rule's own scene (decisions 4–6).
- **How does someone see every scene, block, and rule in an experience at once,
  instead of fetching scene-by-scene?** → Added `GET
  /projects/{projectId}/scenes/full`, a dedicated read-only endpoint returning the
  whole nested tree; the plain scene list stays flat and lightweight for the
  authoring UI's navigator.
- **Does branching (e.g. "if answered correctly go to block Y, if wrong go to block
  N") need a nested or hierarchical rule structure?** → No — it's just two ordinary
  Rule rows with different `event_type`s (`ANSWER_CORRECT` / `ANSWER_WRONG`) on the
  same scene. `Scene.position` is unrelated to this — it only orders scenes in the
  author's editing list, not runtime navigation, which is entirely rule-driven and can
  already branch/skip/loop however the rules say.
- **Does binding a Rule to one specific physical `ScanObject` work once an experience
  runs on more than one box?** → No — a real bug, found while reviewing a colleague's
  independent design exploration. Changed to `scan_object_type_id`, an org-defined
  card type each box can have its own physical instance of. The exact granularity of
  `scan_object_types` (whether it's precise enough for what rules need to
  distinguish) is flagged as still open, needing product input before Phase 3.
- **How does a box know where an experience begins, or reach a scene nothing else
  leads to?** → Added `Scene.is_start` (exactly one per project) and
  `Scene.init_card_type_id` (lets a scene be entered directly via its own card) —
  both missing from the original design entirely.
- **Should score/state variables, rule conditions, and effects be designed now too?**
  → No, deliberately kept out of scope for this proposal — a substantially larger
  feature, left for a future phase.

Nothing is blocking the start of Phase 1.
